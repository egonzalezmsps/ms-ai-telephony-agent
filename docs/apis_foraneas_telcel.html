01

Panorama

Tres llamadas, un objetivo: cambiar de plan

Las tres son POST JSON con el contenido cifrado. Se encadenan mediante el processId.

① createProcess

Abre el proceso de cambio de plan para la línea del cliente.

msisdn→processId
Siempre · primera llamada
/Prod/elegibility/createProcess

② CommunicationMessage

Telcel envía al cliente un SMS con el código de verificación (OTP).

processId→SMS con OTP
Solo si el precio cambia
/Prod/communicationMessage

③ CreateProductOrder

Activa el nuevo plan. Si se envió OTP, Telcel lo valida aquí.

id plan+processId→orden
Siempre · última llamada
/Prod/process/productOrder
02

Cuándo se usa cada una

Dos caminos según el precio del plan nuevo

Todo pasa después de que el cliente escribe ACEPTO o CONFIRMO. Es un flujo determinístico, sin LLM.

Si cualquier API falla: se pide al cliente llamar a Soporte 800 220 9518 OTP incorrecto (BE_MP_BPS_0040) 3 veces: la contratación se bloquea

07

Estado actual

Qué está listo y qué falta

Las tres APIs pueden simularse con TELCEL_xxx_MOCK=true mientras Telcel confirma los datos pendientes.

① createProcess

  • Payload cifrado real
  • Headers con token
  • Sin especificación formal de la respuesta

② CommunicationMessage

  • Cifrado validado en QA
  • Hoy se envían body y headers vacíos
  • El WAF responde a veces 200 y a veces 403

③ CreateProductOrder

  • Headers con token, validados en QA
  • Hoy se envía el body vacío
  • IDs de plan pendientes (MOCK-*)
